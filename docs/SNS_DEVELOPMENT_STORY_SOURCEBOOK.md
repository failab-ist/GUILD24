## 0. 이 문서의 읽는 법

이 프로젝트의 개발 스토리는 단순히 “아이디어를 내고 AI로 게임을 만들었다”가 아니다.

실제로는 다음 흐름에 가깝다.

1. 게임을 만들 생각이 없던 비개발자가 AI로 업무 도구를 만들기 시작함.
2. “코드를 몰라도 실제로 돌아가는 소프트웨어를 만들 수 있다”는 경험이 쌓임.
3. 브라우저에서 완결되는 작은 게임을 만들어보자는 시도가 시작됨.
4. 여러 게임 아이디어 중 Dungeon Shop이 살아남아 《던전 앞 편의점》이 됨.
5. 처음에는 기능과 콘텐츠를 빠르게 늘렸지만, 실제 플레이·시뮬레이션에서 문제가 드러남.
6. 이후 개발 방향이 “기능 추가”보다 “의미 있는 선택을 남기는 것”으로 바뀜.
7. AI에게 구현을 맡기는 방식도 채팅 중심에서 Git / SSOT / Director / Work / QA 체계로 변화함.
8. 게임 규칙뿐 아니라 UI, 픽셀아트, 로고, BGM, 카피까지 반복적으로 실패하고 다시 깎음.
9. 후반에는 “테스트가 통과했는가”보다 “사람이 실제로 플레이했을 때 의도한 경험이 생기는가”를 더 중요하게 보기 시작함.

이 흐름 자체가 가장 큰 개발기 서사다.

# PART 1. 게임을 만들기 전 — 이미 “AI로 만드는 사람”이 되고 있었다

## 2026-07-24 — 게임보다 먼저 만든 것은 업무용 검수 툴

당시 사용자는 개발자가 아니었고, Claude 기반 바이브코딩으로 브라우저에서 돌아가는 업무용 HTML 툴을 만들고 있었다.

확인된 당시 규모:

- app.js 약 1,888줄
- 약 104KB
- 일반 함수 약 90개
- 화살표 함수 수백 개
- DOCX / PPTX / XLSX를 ZIP/XML 수준에서 읽음
- 파일 파싱
- 룰 기반 검수
- AI 검수
- 설정
- UI
- 결과 생성까지 한 브라우저 툴 안에서 처리

중요한 점은 “코드를 생성했다”가 아니라 실제 업무 문제를 해결하면서 버그를 고쳤다는 것.

예를 들어 문서에 들어 있는 사진을 세어 인스타 원고를 검수하는 기능을 만들었고,
실제 이미지 35장을 사람별 14 / 12 / 9장으로 집계했다.

그 과정에서 AI가 인물을 재배분하면 기존 체크/메모 상태가 사라지는 버그가 발생했고,
단순 UI 상태가 아니라 SHOTS 데이터 쪽에 상태를 보존하도록 구조를 바꿨다.

### SNS 소재

**“내 첫 바이브코딩 프로젝트는 게임이 아니었다.”**

게임 개발 이전부터:
- 실제 파일을 읽고
- 실제 업무 규칙을 적용하고
- 실제 버그를 잡고
- 데이터가 사라지지 않게 구조를 바꾸는 경험을 이미 하고 있었다.

게임 개발은 갑자기 시작된 도전이라기보다,
“AI로 실제 제품을 만드는 경험”이 게임으로 확장된 다음 단계에 가깝다.

---

## 2026-07-28 — “이걸 개인 프로젝트로 공개할 수 있나?”

이때부터 단순 사내용 툴이 아니라 GitHub에 올릴 수 있는 개인 프로젝트 가능성을 고민하기 시작했다.

논의된 방향은:
- README 정리
- incremental commit
- Claude / ChatGPT 도움을 숨기지 않되
- 구조 판단, 기능 설계, 테스트, 통합은 제작자가 주도했다는 점을 보여주는 방식

즉, 이미 이 시점에
“AI가 코드를 썼다”보다 “내가 무엇을 결정했는가”를 보여줘야 한다는 문제의식이 있었다.

이 관점은 이후 《마왕 잡는 편의점》 개발 방식과 거의 그대로 이어진다.

---

## 2026-07-30 — “계속 설계만 하지 말고 실제로 돌려보자”

게임과 별개로 money-bot이라는 자동 콘텐츠 파이프라인도 설계했다.

대략적인 흐름은:

RSS / 뉴스 수집
→ 필터링
→ LLM 요약·스크립트
→ Telegram 승인
→ CapCut용 에셋/렌더링
→ 수동 발행
→ 성장 로그

이때 사용자가 명확히 잡은 태도가 하나 있다.

**계속 설계 리뷰만 하지 말고 일단 코딩해서 실제로 운영해보자.
부족한 것은 실제로 돌려봐야 보인다.**

이 원칙이 이후 게임에서도 반복된다.

- 숫자는 플레이해보고 바꿈.
- 체감 이상은 시뮬레이션으로 확인함.
- UI는 Source에 존재하는 것으로 끝내지 않고 실제 클릭으로 검증함.
- 디자인도 프롬프트 한 번으로 끝내지 않고 실제 출력물을 보고 재지시함.

### 개발기 서사의 프롤로그로 쓸 수 있는 핵심

“게임 개발 경험 0 → 어느 날 갑자기 게임 제작”보다 사실에 가까운 서사는:

**업무 자동화 툴을 만들다가,
AI와 함께 복잡한 시스템을 실제로 고쳐나가는 법을 익혔고,
그 다음에 ‘그럼 게임도 만들 수 있지 않을까?’로 넘어갔다.**

# PART 2. 2026-09-08 — 게임 아이디어 탐색이 시작되다

## 시작 조건부터 꽤 구체적이었다

초기 게임 탐색에서 잡힌 조건:

- 실시간 액션이 아닌 턴제
- 외부 API나 서버 없이 코드 내부에서 완결
- 브라우저에서 실제 플레이 가능
- 나중에 외부 공개 가능한 프로젝트
- 반복 플레이가 가능해야 함
- 너무 텍스트 위주여서는 안 됨
- 대중적으로 이해 가능한 훅이 필요함

즉 처음부터 “AI가 만들기 쉬운 게임”만 찾은 것이 아니라,
제작 가능성과 플레이 가능성을 동시에 보려고 했다.

---

## 초기 후보군

초기 후보로 확인되는 이름은:

- LAST MART
- 9 to 6
- Dungeon Shop
- Tiny Guild
- The Deal

모든 후보의 원문 설명이 현재 검색으로 완전히 복구되지는 않았지만,
Last Mart / Dungeon Shop / Tiny Guild는 비교적 명확하게 남아 있다.

### LAST MART

포스트아포칼립스 편의점 운영.

- 낮에는 생존자에게 물자를 판매
- 밤에는 인력/방어 관련 판단
- 아이템 조합으로 생존 도구 생성
- NPC / 사건 / 결과를 로컬 JS 규칙으로 조합

당시 제안 단계에서는 강한 후보였다.

### TINY GUILD

- 랜덤 모험가 영입
- 스탯 / 특성 / 장비 조합
- 3인 파티 원정
- 자동전투
- 영구사망
- API 없이 조합형 콘텐츠로 반복성 확보

사용자 반응은 흥미롭지만 동시에 현실적인 걱정이었다.

**“웹게임으로 내가 상상하는 수준까지 구현되나?”**
**“그래픽을 넣을 수 있나?”**
**“텍스트만 보면 지루하지 않나?”**

이 질문이 중요하다.

이 게임은 처음부터 “텍스트 로그라이크라도 되면 됨”이 아니었다.
게임 플레이를 시각적으로 느끼게 만드는 것이 초기부터 조건이었다.

---

## Dungeon Shop이 살아남다

Dungeon Shop 방향에서
“한국식 요소를 섞으면 《던전 앞 편의점》이 어떠냐”는 쪽으로 이름과 세계가 빠르게 수렴한다.

초기 제안 루프는 대략:

편의점 경영
→ 모험가에게 판매
→ 모험가가 던전에 감
→ 결과가 돌아옴
→ 재료/경제/상품에 다시 영향

조금 더 닫힌 형태로는:

**편의점 → 모험가 → 던전 → 재료 → 상품 → 편의점**

여기서 Tiny Guild와의 중요한 차이가 생긴다.

Tiny Guild는 플레이어가 “모험가 파티를 직접 굴리는 사람”에 가깝다.

던전 앞 편의점은
플레이어가 전투를 하지 않으면서도
모험가의 결과에 개입할 수 있다.

나중에 이 차이가 현재 Game Vision의 핵심 문장으로 정제된다.

**“플레이어는 직접 싸우지 않는다. 대신 싸우러 가는 사람들의 미래에 개입한다.”**

# PART 3. 첫날부터 단순 상점 게임으로 두지 않았다

## “운빨과 런 차이가 더 커야 한다”

초기 아이디어 직후 사용자 쪽에서 바로 나온 요구 중 하나가
상품과 모험가의 희귀도,
그리고 런마다 강하게 달라지는 RNG였다.

단순히:
- 물건 사서
- 물건 팔고
- 돈 버는

경영 시뮬레이션으로 끝내고 싶지 않았던 것.

초기 논의에서는 다음이 빠르게 붙는다.

- 상품 희귀도
- 모험가 희귀도
- 런 RNG
- 30일 단위 런
- 런 종료 후 초기화
- 상품 해금
- 직업 해금
- 설비 해금
- 몬스터 지식
- 시작 특전
- 런 중 점포 업그레이드

즉 첫날부터 이미
“편의점 경영 + 모험가 육성 + Roguelite Build”를 하나로 합치려는 방향이었다.

# PART 5. 같은 날 — 기능 추가보다 먼저 수치 실험이 시작됐다

## 가격은 50% / 100% / 150%

현재까지 이어진 대표적인 규칙 중 하나가:

- 반값
- 정가
- 바가지

세 가격 선택이다.

하지만 이것을 단순 flavor 선택으로 둔 것이 아니라
모험가 육성과 점포 경제가 충돌하는 의사결정으로 만들었다.

반값은 모험가 투자에 유리하지만 돈이 부족해지고,
바가지는 가게 수익에 좋지만 구매/성장에 영향을 준다.

---

## 시설은 점포지원 / Relic Build로 변한다

초기 “설비” 개념은 이후
런 중 선택하는 점포지원 / Relic 구조로 재정의된다.

확인되는 당시 방향:

- Relic 약 30종
- 런 중 여러 차례 선택
- 후보 중 선택 또는 보류
- 서로 다른 점포 Build를 만들기

이것은 나중에
박리다매 / 단골 육성 / 고마진 / 원정 전문 / 신선식품 / 상권 등
서로 다른 운영 방향으로 세분화된다.

---

## Dungeon도 “던전 5개”에서 Family × Tier 구조로

단순 던전 목록이 아니라
Family와 Tier를 나눠
같은 계열도 위험이 달라지는 구조로 바뀐다.

이후 Hazard 시스템이 별도 축으로 분리되면서
“던전 이름을 외우는 게임”보다
“오늘 공개된 위험을 보고 무엇을 준비할지 판단하는 게임” 쪽으로 이동한다.

# PART 6. 4,800회 시뮬레이션 — 감으로 만든 숫자를 바로 의심하기 시작함

첫날부터 다중 시뮬레이션이 돌기 시작했다.

확인된 4,800회 결과 예시:

- 핵심 NPC를 선택적으로 투자하는 전략의 클리어율 약 50.7%
- 정가 중심 약 20.3%

# PART 8. 게임 화면도 처음에는 한 화면에 너무 많은 것을 넣었다

**“게임 기능은 다 있었는데 게임 같지 않았다.”**

실제 손가락으로 플레이하자

# PART 13. 2026-09-11 — 게임을 만든 뒤에야 “이 게임이 뭔지” 다시 정의했다

여러 시스템이 이미 존재한 상태에서
Lean Game Vision을 다시 뽑았다.

최종적으로 남은 문장:

**《마왕 잡는 편의점》은 RPG 세계를 편의점 카운터 뒤에서 플레이하는 턴제 경영 로그라이트다.**

**플레이어는 직접 싸우지 않는다.
대신 싸우러 가는 사람들의 미래에 개입한다.**

Core Fun:

**관찰 → 추론 → 선택 → 결과 확인 → 기억 → 다음 판단**

Phase별 재미도 다시 정의됐다.

- MORNING = 상황 파악 / 예측
- ORDER = 자원 배분 / 선제 판단
- SALE = 사람 읽기 / 이익 vs 투자
- NIGHT = 결과 확인 / 인과관계
- CLOSING = 회고 / 계획 수정
- FINAL = 누적 판단의 결산

여기서 중요한 변화는
게임을 시스템 목록으로 설명하지 않게 된 것.

“상품 30개, 이벤트 22개가 있는 게임”이 아니라
“내가 한 작은 경영 판단이 나중에 사람의 생존과 성장으로 돌아오는 게임”이 된다.

# PART 28-A. 2026-10-10 — 출시 직전, 같은 이름의 게임을 찾았다

앱 출시 준비를 하던 중에
다른 AI(GPT)가 같은 이름의 게임이 이미 있다고 알려 왔다.

2020년에 나온 모바일 게임 「던전 앞 편의점」이었다.
직접 검색해 보니 사실이었다.

한 달 넘게 부른 이름이었고,
로고 받침 ㅁ 하나까지 고쳐 가며 다듬은 글씨였다.
그래도 스토어에 같은 이름 두 개가 나란히 뜨면
찾는 사람도 헷갈리고 우리 게임도 묻힌다.

그래서 이름을 바꾸기로 했다.

## 후보를 고른 기준

- 「마왕성 앞 편의점」 — 옛 이름에서 한 단어만 바꾼 꼴이라 여전히 헷갈렸다.
  게다가 가게는 게이트 앞에 있고, 마왕성은 마지막 날에만 가는 곳이다.
- 「길드24: 마왕 잡는 편의점」 — GUILD24는 뒤에 붙는 게 낫다고 봤다.
- 「마왕 잡는 편의점: 길드24」 — 최종 선택.
  「좀 유치해 보이지 않을까」 하는 걱정도 있었다.
  그래도 무슨 게임인지 바로 말해 주는 제목이라 이걸로 정했다.

플레이어는 직접 싸우지 않는다.
그런데 마지막에 마왕을 잡는 건
내가 판 물건을 들고 간 모험가들이다.

**“편의점이 마왕을 잡는다”는 말이
이 게임이 무엇인지를 한 줄로 설명한다.**

GUILD24는 뒤로 갔다.
게임 속 간판 브랜드로 남고,
슬로건 「던전 가기 전, 길드24.」도 그대로다.
프롤로그 첫 문장 「나는 던전 앞에 편의점을 차렸다.」도 남았다.
가게가 던전 앞에 있는 건 바뀌지 않았기 때문이다.

## 로고를 다시 그렸다

새 로고는 사용자가 직접 그렸다.
두 줄과 한 줄, 부제 있음과 없음을 실제 게임 화면에 넣어 비교했고
결국 부제 없는 한 줄 「마왕 잡는 편의점」이 남았다.

그리고 또 「점」의 받침 ㅁ이 ㅁ처럼 안 읽혔다.
처음엔 가운데 구멍을 키웠는데 너무 과했다.
결국 구멍은 그대로 두고 테두리 모서리만 각지게 다듬었다.

## 바뀌지 않은 것

앱 ID와 세이브 저장 이름은 처음부터 GUILD24 기준이었다.
그래서 이름을 바꿔도 기존 세이브는 그대로 이어진다.

### 콘텐츠 포인트

**“출시 직전에 이름을 잃었는데, 오히려 게임을 더 잘 설명하는 이름을 얻었다.”**

현재 상위 Vision:

**정보는 쉽게, 결정은 어렵게.**

그리고:

**관찰 → 추론 → 선택 → 결과 확인 → 기억 → 다음 판단**

돌이켜보면 대부분의 변경이 이 방향으로 설명된다.

### 제거된 것
- 숨은 직업 보너스
- 설명하기 어려운 콤보
- 중복 피로 대응
- 불필요한 UI ornament
- 죽은 문서
- 의미 없는 리팩터링

### 강화된 것
- 오늘의 위험을 읽는 정보
- 발주에서의 자원 배분
- NPC별 가격/투자 판단
- 결과의 원인 설명
- 부상/사망/성장의 기억
- 다음 날 의사결정에 돌아오는 결과

즉 개발 과정은
“콘텐츠를 더 넣은 역사”보다

**플레이어가 무엇을 보고 무엇을 고민해야 하는지를 계속 깎아낸 역사**

에 더 가깝다.

## C. 밸런스 / 데이터

### 8. 첫날부터 4,800판을 돌린 이유
감으로 만든 경제를 전략별로 비교.

### 9. 운영비를 5G 올렸는데 아무 일도 일어나지 않았다
효과 없는 밸런스 조정은 폐기.

### 10. “화염만 너무 자주 나오는데?”
2만 Run 확인 → 실제로는 거의 동일 → 체감이 틀린 사례.

### 11. 대성공이 너무 자주 뜬다고 바로 확률을 Nerf하지 않은 이유

### 12. 유물 밸런스를 ‘강함 점수’로 매기지 않은 이유
DAY5의 200G와 DAY25의 200G는 같은 가치가 아님.

### 13. 돈은 벌었는데 게임에서는 졌다
Fresh Run “부유하지만 원정대가 죽은 점포”.

### 14. 첫 판과 두 번째 판의 원인이 달랐다
성공률 문제처럼 보였지만 반복 신호는 부상→사망.

## E. 게임 디자인

### 19. 직업 / 특성 / 아이템 / 유물의 역할을 일부러 갈라놓은 이유
플레이어가 “왜 실패했는지” 알 수 있게.

### 20. 전투를 안 하는 RPG를 만든다는 것

# PART 36. 이 프로젝트를 소개할 때 피해야 할 단순화

## X: “AI에게 게임 만들어달라고 해서 만들었다.”

너무 많은 핵심이 사라진다.

더 정확한 표현:

**AI를 사용해 직접 만들었지만,
게임의 방향과 판단 기준을 세우고
AI가 만든 결과를 플레이·데이터·QA로 계속 반박하면서 완성도를 올린 프로젝트.**

---

## X: “몇 주 만에 게임 하나 완성.”

속도 자랑만 남으면 양산형 AI 프로젝트와 구분되지 않는다.

더 강한 서사:

**짧은 기간 동안 기능을 많이 만든 것이 아니라,
빠르게 만든 것을 실제 플레이로 부수고 다시 설계하는 사이클을 여러 번 돌렸다.**

---

## X: “AI Agent 여러 개를 사용한 멀티에이전트 개발.”

기술 이름만 나오면 재미가 없다.

실제 포인트:

**에이전트가 많아질수록
누가 디자인을 바꿀 수 있고,
누가 코드만 고칠 수 있고,
무엇을 현재 정답으로 봐야 하는지를 더 엄격히 정해야 했다.**

# PART 38. 현재 기준의 한 문장

게임의 최종 방향과 개발 과정의 공통점은 같다.

**“정보는 쉽게, 결정은 어렵게.”**

플레이어에게도,
AI 에이전트에게도,
무엇을 보고 판단해야 하는지는 명확하게 주되
실제 결정을 자동으로 대신하게 하지 않는 방식으로 발전했다.

---

# 자료 신뢰도 메모

이 문서는 세 종류의 근거를 섞어 사용한다.

### A. Past Chat Confirmed
과거 ChatGPT 대화 검색에서 날짜와 발언/결과가 직접 확인된 내용.

### B. Project / Source Confirmed
현재 Project Sources, 초기 저장 파일, Git/Source 기록에서 확인된 내용.

### C. Editorial Interpretation
여러 사건을 SNS 개발기 관점에서 연결한 해석.
게임 규칙의 Canonical로 사용하면 안 된다.

초기 후보 중 9 to 6 / The Deal은 현재 검색 가능한 과거 기록에서 세부 원문이 충분히 복구되지 않았다.
후속으로 원문이 발견되면 이 문서에 추가하되, 추측해서 채우지 않는다.

---

# 현재 게임의 Canonical과의 관계

현재 Game Vision은 다음을 핵심으로 둔다.

- RPG 세계를 편의점 카운터 뒤에서 플레이하는 턴제 경영 로그라이트
- 플레이어는 직접 싸우지 않고 싸우러 가는 사람들의 미래에 개입
- 관찰 → 추론 → 선택 → 결과 확인 → 기억 → 다음 판단
- NPC가 감정적 중심
- 기능 수보다 의미 있는 Player Decision 우선
- 한 Run이 끝났을 때 “이번 판은 이런 가게였다”는 기억

이 문서는 그 결론이 처음부터 완성되어 있었던 것처럼 보이게 하지 않는다.

오히려:
**수많은 추가 / 삭제 / 실패 / 측정 / 플레이테스트 끝에
이 몇 문장으로 수렴한 과정 자체를 기록한다.**
