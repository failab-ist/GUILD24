# 코드베이스 리뷰 — v2.4 종료 시점

**왜 했나.** v2.4를 닫고 v2.5로 넘어가기 전에, 이 코드가 계속 개발하기 좋은 상태인지
확인해 달라는 요청. 인상이 아니라 실측으로 판단하고, 나온 문제를 그 자리에서 고쳤다.

**결론.** 계속 개발해도 된다. 구조는 건강하고 성능은 여유가 있으며 안전망(전체 테스트 7.5초)이
이미 있다. 아픈 곳은 **파일이 크다는 문제가 아니라 한 줄이 너무 길다는 문제**였고, 가장 심한
네 곳을 고쳤다.

## 2. 고친 것

### 2-1. 저장 검증기가 한 줄에 5,048자 · 분기 126개였다

**문제.** `Save.valid()`는 저장 무결성을 지키는 함수인데 전체가 한 줄이었다. 한 글자만 고쳐도
`git diff`는 `+1 −1`로 나오지만 그 한 줄이 5,048자라 **무엇이 바뀌었는지 눈으로 볼 수 없다.**
v2.4에서만 두 번 확장했고(통합 계약, 손님 대사), v2.5에서 캐릭터 ID와 Job Mastery 상태가
저장되면 또 건드릴 자리다.

**처리.** 이름 붙은 검사 8개로 나눴다 — 계정 / Run 뼈대 / 명단 / 모험가 / 재고 / 진행 상태 /
최종 구성 / 점포지원 갱신. `read` `write` `import` `export`도 함께 읽히게 폈다.
**동작은 한 글자도 바꾸지 않았다.**

**증거.** 구·신 버전을 나란히 로드해 **4,840개 케이스**(실제 진행 중 저장 스냅샷 88개 × 변종
54종 — 필드를 하나씩 망가뜨린 것)에 대해 판정을 대조했다. **불일치 0건.**
최장 줄 5,278자 → 155자.

> 리팩터링이 동작을 바꾸지 않았다는 것은 "테스트가 통과했다"로는 부족하다. 구현을 둘 다
> 돌려서 같은 답을 내는지 직접 비교하는 것이 증거다.

### 2-2. `meta.js`가 한 줄에 754자였다

**문제.** 파일 자체는 1.7KB로 작지만 `observe()`가 한 줄이었다. v2.5의 Job Mastery 재설계가
가장 먼저 건드릴 파일이다.

**처리.** 함수별로 폈고, 등급 문턱값에 이름을 줬다. 던전 지식이 "보급받은 모험가가 살아
돌아왔을 때만" 쌓인다는 규칙을 주석으로 명시했다. 동작 변경 없음.
최장 줄 754자 → 119자.

### 2-3. 키보드 포커스가 매 행동마다 사라졌다

**문제.** 화면을 다시 그릴 때 `#app`을 통째로 갈아끼운다. 스크롤 위치는 누군가 이미 보존해
뒀는데 **포커스는 보존하지 않아서**, 키보드나 스크린리더 사용자는 상품을 하나 고를 때마다
화면 맨 처음으로 튕겼다. 마우스로는 보이지 않는 문제다.

**처리.** 다시 그리기 직전에 포커스된 조작 대상을 기억했다가, **화면이 그대로인 경우에만**
같은 자리로 되돌린다. 화면이 바뀌는 경우는 기존대로 새 화면 본문으로 간다(그게 맞다).
대상은 위임 클릭이 이미 쓰는 `data-action`/`data-id`로 찾으므로 새 체계를 만들지 않았다.

**1차 처리는 절반만 맞았다 — 마감 정리에서 고쳤다.** `data-action`/`data-id`만으로는 조작
대상이 하나로 특정되지 않는다. 발주 화면의 수량 다이얼은 **버튼 30개가 같은 `data-action`을
쓰고 `data-id`가 없다.** 첫 일치를 가져오는 방식이라 1차 구현은 실제 브라우저에서 이렇게
동작했다.

| 상황 | 1차 구현 | 마감 정리 후 |
| --- | --- | --- |
| 4번째 상품의 `+`를 누름 | **포커스가 `<body>`로 떨어짐** (첫 일치인 1번 상품 `−`가 비활성이라 포커스를 못 받음) | 누른 `+`에 그대로 |
| 1번 상품에 수량이 있을 때 같은 조작 | **1번 상품의 `−`로 이동** — 엉뚱한 상품의 감소 버튼 | 누른 버튼에 그대로 |
| 수량을 0까지 내려 `−`가 비활성이 됨 | 포커스가 `<body>`로 떨어짐 | 같은 다이얼의 살아 있는 `+`로 |
| 아침 화면, 점포지원 링크에 포커스 | 유물 진열 버튼으로 이동 (같은 키를 2개가 공유) | 링크에 그대로 |

즉 **가장 많이 반복해서 누르는 화면에서 이 수정은 동작하지 않았고, 동작할 때는 엉뚱한
버튼을 잡았다.** 원인은 하나다 — 키가 유일하지 않은데 첫 일치를 썼다.
이름표에 **같은 키를 쓰는 것들 사이에서의 위치**를 더했고, 누른 그 조작이 방금 비활성이 된
경우(수량을 0이나 상한까지 민 경우)에는 같은 그룹의 살아 있는 이웃으로 넘긴다.

**증거.** 실제 브라우저에서 위 표의 네 경우를 모두 돌려서 확인했다. 화면이 바뀔 때
`#phase-content`로 가는 것, 모달이 열려 있는 동안 아래쪽 다시 그리기가 모달에서 포커스를
빼앗지 않는 것도 같이 확인했다. 이 확인은 `npm run qa:visual`에 실제 동작 검사로 들어가 있다.

### 2-4. 테스트 실행이 전부 수동이었다

**문제.** 7.5초짜리 훌륭한 테스트가 있는데 **돌리는 걸 잊으면 그만**이었다. CI도 없다.

**처리.** `tools/hooks/pre-commit` 추가. `npm run hooks` 한 번으로 설치되고, 이후 커밋마다
전체 테스트가 돈다. 실패하면 커밋을 멈추고 실패 부분을 보여준다.
정말 필요할 때는 `git commit --no-verify`로 우회할 수 있다.

## 3. 일부러 하지 않은 것

### `app.js` 분리 — 지금은 하지 않는 게 맞다

`app.js`는 61KB / 537줄로 소스의 29%이고, `renderModal` 하나가 9,467자, 액션 분기가 47개다.
"한 파일에 너무 몰려 있다"는 지적은 **맞다.** 그런데 조사해 보니 지금 쪼개는 건 손해다.

1. **이 파일은 즉시실행 함수로 감싸여 있다.** 54개 함수와 15개 상단 바인딩이 하나의 사설
   스코프를 공유한다. 파일을 나누려면 그 스코프를 열어 전역으로 빼거나 파일 간 이름 전달
   체계를 새로 만들어야 한다 — 어느 쪽도 "파일만 나누는" 작업이 아니다.
2. **밀도를 먼저 풀지 않으면 효과가 없다.** 15KB짜리 4개에 2,000자 줄이 그대로 있으면
   편집 난이도는 똑같다.
3. **버그를 고치는 작업과 구조를 갈아엎는 작업을 같이 하면 회귀 위험만 커진다.**

**앞으로.** 나눌 자연 경계는 이미 있다 — 화면 빌더 / 모달 / 액션 디스패치. 다만 이건
**예약이 아니다.** 이 파일을 수정한다는 사실 자체는 분리 사유가 되지 않고, v2.5의 어떤 작업이
여기를 건드린다는 것만으로도 분리 사유가 되지 않는다. 분리는 **이 파일에서 작업하는 비용이
실제로 올라갔다고 측정됐을 때** 다시 꺼내는 선택지다. 그때의 순서는 밀도 정리 → 분리이고,
버그 수정과 섞지 않는 단독 작업으로 한다.

### 전면 자동 포매팅 — 측정해 보니 손해였다

prettier로 전체를 돌려 봤다:

| | 이전 | 이후 |
| --- | --- | --- |
| 바이트 | 163KB | 223KB (**+36.4%**) |
| 줄 수 | 1,252 | 5,999 (4.8배) |
| 최장 줄 | 5,278자 | **2,074자** |

+36%의 컨텍스트 비용을 내고도 **최악의 줄은 안 풀린다.** 포매터는 문자열 연결을 쪼개지
못하기 때문이다. 이 프로젝트는 토큰 효율이 명시된 제약이므로, 전면 포매팅 대신 **아픈 로직
함수만 손으로 푸는 쪽**을 택했다. 500자 넘는 줄 36개 중 로직이 27개(24,045자)이고
템플릿이 9개(8,478자)인데, 템플릿은 검색으로 편집하므로 덜 아프다.

## 4. 문제처럼 보였지만 아니었던 것

여기에 시간을 쓰지 않아도 된다. 전부 확인한 결과다.

- **전역 14개(`G.*`)** — 모듈 시스템이 없는 건 의도다(빌드 스텝 0, 파일 열면 실행).
  이름 충돌 없고 네임스페이스가 깔끔하다.
- **레이어 분리** — `systems`가 `ui`를 참조하지 않는다. 유일한 예외 `simulation.js`는 QA
  도구다. UI가 엔진을 우회해 상태를 쓰는 곳도 3군데뿐이다.
- **중복 코드** — 3회 이상 반복되는 동일 줄이 10종. 사실상 없다.
- **전면 다시 그리기** — 턴제라 초당 60프레임이 필요 없고 13.7ms면 충분하다. 가상 DOM
  도입은 순손해다.
- **조용히 삼키는 `catch`** — 3곳 전부 정당하다. 저장 읽기는 최신본이 깨지면 백업으로
  내려가야 하고, 시뮬레이션은 발주 가능 여부를 시도로 탐색한다.
- **엔진 상수의 UI 복제** — 자동 검색에는 `22`가 양쪽에 있다고 나오지만, UI 쪽은 애니메이션
  픽셀값이었다. 복제 아님.
- **죽은 CSS** — 자동 검출로는 16개가 나왔는데 **전부 오탐이었다.**

> ### 이 코드베이스에서는 정적 검색 결과를 그대로 믿으면 안 된다
>
> 클래스 이름이 `'stage p-'+phase`, `'t-'+tone`처럼 **실행 중에 조합된다.** `grep`으로는
> 안 걸린다. 이번에도 `.p-order`를 "죽은 규칙 6개"로 보고할 뻔했다가, 실제 브라우저에서
> DOM을 열어 보고 살아 있다는 걸 확인해서 멈췄다. `.t-great`/`.t-safe`도 같은 경우였다.
>
> **지우기 전에는 반드시 실행해서 확인한다.** 확신이 없으면 두는 쪽이 안전하다.

## 6. 남은 것

- **`app.js` 분리 — 계획 없음.** §3 참조. 검토하고 하지 않기로 한 항목이다. 파일을 건드리는 것
  자체는 분리 사유가 아니며, 재검토 조건은 "작업 비용이 실제로 올라갔다는 측정"이다.
- **한글 주석의 폰트 비용 — 되돌렸다.** 폰트 서브셋 검사가 `dist` 안 모든 글자를 훑기 때문에,
  한글 주석을 늘리면 배포 폰트가 커진다. 이 리뷰가 넣은 주석 때문에 요청 글자가 23자 늘어
  **+4,336바이트(+2.4%)**가 됐었다. 마감 정리에서 **이 리뷰가 새로 넣은 엔진 주석만** 영어로
  바꿔서 요청 글자 714자 · 폰트 5개 · `coverage.json`을 전부 **이전과 바이트 단위로 동일**하게
  되돌렸다. 화면에 나가는 한국어 문자열은 하나도 건드리지 않았다.
  서브셋 검사에서 주석을 빼는 편이 더 정확하지만 문자열 안의 `//`를 오인하지 않는 파서가
  필요해서 **만들지 않았다.** 대신 규칙으로 둔다 — 엔진 주석은 ASCII로 쓴다.
- **CI** — pre-commit은 로컬 방어선이다. 원격 CI는 아직 없다.

## 7. 검증

이번 작업 전체에 대해:

```
npm test        통과, 실패 0 — 16묶음 147검사 (이전 145 + 이번에 추가한 2)
npm run qa:visual  clean, 21장 + 키보드 포커스 실동작 검사
Save.valid 동치  4,840 케이스 대조, 불일치 0
포커스 보존      실브라우저 확인 — 같은 화면 유지 / 비활성이 된 조작 / 열린 모달 / 화면 전환
폰트 baseline   요청 글자 714자, WOFF2 5개 + coverage.json 모두 리뷰 이전과 동일
```

고친 것은 전부 테스트로 박았다.
- 저장 검증기가 이름 붙은 검사로 남아 있는지 + 각 절이 여전히 거절하는지 (`tests/integration.cjs`)
- 같은 화면 다시 그리기에서 포커스가 유지되는지 — `npm test`는 DOM이 없으므로 연기 감지용
  구조 검사만 하고(`tests/ui-guard.cjs`), **실제 동작은 브라우저에서** 돌린다
  (`tools/qa-visual.cjs`). 1차 구현의 결함은 구조 검사로는 잡히지 않았고 실동작 검사로만
  잡혔다 — 이 항목에서 배운 것이다.

게임 규칙·수치·설계 문서는 하나도 바뀌지 않았다. `canonical/` 변경 0, `dist/data/` 변경 0,
`bossPower 230` · `operating 60` 그대로다.
