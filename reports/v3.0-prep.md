2. 앱용 local persistence를 연결하고, v3.0 public Save boundary를 구현한다.

5. signing / versionCode / AAB를 구성하고 실제 Android 기기에서 release-owner QA를 통과시킨다.
**C. Play 행정 / 스토어 준비**
1. 개인정보처리방침 URL과 Google Play Data Safety를 PGS v2/Saved Games 실제 연동 기준으로 작성한다. 별도 Analytics를 추가하면 다시 갱신한다.
2. 광고 여부, 대상 연령, 앱 접근, IARC 등급 설문 등 Play Console 필수 항목을 채운다.

### 7-3. 가로로 돌린 폰 — PC 레이아웃을 가져다 쓸 수 있나 (2026-09-28 캡처 점검)

932x430(지금 가로 폰 화면)과 1024x430(PC 레이아웃을 같은 높이에 넣은 것)을 SALE · ORDER · NIGHT · MORNING으로 찍어 봤다.
- **안 된다. 막히는 건 폭이 아니라 높이(약 400px)다.** PC 레이아웃은 세로 약 800px 이상을 전제로 짜여 있다(1366x768 노트북에서도 진열대가 4줄만 보임).
  430 높이에 넣으면 SALE은 진열대가 한 줄도 안 보이고, ORDER는 합계 칸만 보이고 상품 행이 하나도 안 보인다.
- 지금 가로 폰 화면도 같다: SALE은 손님·목적지·능력치만 보이고 진열대가 화면 밖, NIGHT는 결과 카드가 잘린다.
  MORNING만 볼 만하다. 가로 화면에서 화면 QA 한 건(SALE 카드 묶음 크기)도 실패한다.
- 가로를 제대로 하려면 **가로 전용 배치**(왼쪽 손님·정보, 오른쪽 진열대, 버튼은 옆 세로 띠)가 따로 필요하다.
  이 배치는 Steam PC 화면에도 그대로 이어질 수 있다(가로 16:9 구성 하나를 크기만 바꿔 폰 가로 · 태블릿 가로 · PC에 쓰기). v3.x Steam 이식 때 같이 하는 게 맞다.
- **v3.0(모바일)은 세로 고정으로 간다.** 안드로이드 16(API 36)부터 태블릿·폴더블에서는 앱의 화면 방향 고정이 무시되지만,
  `android:appCategory="game"`인 게임은 예외라 세로 고정이 유지된다. 구글 플레이는 2026-08-31부터 새 앱과 업데이트에 API 36 타깃을 요구한다.

### 8-4. 출시 전 게임 경험 확인

현재 게임 안쪽의 필수 잔여는 기능 추가가 아니라 검증이다.

1. User 최신 빌드 실플레이.
2. 가능하면 처음 하는 사람의 첫 10분/D1~D3 관찰.
3. 실제 폰에서 템포·가독성·끊어 하기 확인.
4. 지적이 나온 항목만 최소 수정한다.

새 기능을 선제적으로 추가하지 않는다. 플레이 피드백이 없는 상태에서 보류 후보를 승격하지 않는다.

### 8-5. v3.0+ 보류 후보

일일 보상 줄 `어제보다 +N`, ORDER 허용 범위 표시, 원정 목적 확장, 점포 빌드 축 확장, 단골 관계 심화,
Final/마왕 확장, 상품 기록, 아이템 대량 추가, 세계관/아트 확장은 **v3.0 출시 필수 범위가 아니다**.
현재 Core Fun 또는 출시 차단 문제를 해결하지 않는 한 승격하지 않는다.

### 8-6. 현재 결론

**v3.0의 게임 내 작업은 대규모 기능 추가 단계가 아니다.**
v2.11.1을 기준으로 실플레이 → 필요한 미세 조정 → 출시 준비 순서로 간다.

### 9-10-2. NIGHT 스탬프 반전 제안 — 중요/희귀하게 쓰기

**User 제안:** \`중상 → 퇴각\` 등 판매 상품이나 만반의 준비가 실제 결과를 바꿨다면, 기존 위험한 판정 스탬프가 먼저 찍힌 뒤 최종 판정 스탬프로 덮어써져야 한다. 뚜렷한 타격감은 원하지만 매번 남발해 감흥이 떨어져서는 안 된다.

**현재 구현:** PRESENTATION H1 / UI_UX §NIGHT LAYOUT — VERDICT STAMP는 \`rescued\`/\`avoidedDeath\` 및 사망이 만반의 준비로 회피된 경우에만 2단 전환을 허용한다. 기존 NIGHT_CLOSING은 귀환석·세계수 생환부적의 실전환뿐 아니라 구급키트 중상→부상 등 실제 Outcome 강하, \`heroProof.outcome\`의 제거 비교를 별도로 기록한다. **현행 '강골·구급키트는 반전 금지' 계약을 수정하지 않고도 자동으로 확대 적용할 수는 없다.** 추가 2단 연출은 명시적인 User 승인이 있어야 하며 PRESENTATION / UI_UX / NIGHT_CLOSING / QA를 함께 개정해야 한다.

**핵심 구분:**
1. **실제 판정 경로에서 직접 확정되는 전환** — 보험류(세계수 생환부적: 사망/중상 → 퇴각, 귀환석: 부상/중상/사망 → 퇴각), 구급키트(중상 → 부상), 만반의 준비가 사망을 막아 부상/중상으로 바꾼 경우 등 *실제 증거가 있는 결과쌍*. 기존 2단 연출이 적용된 죽음 회피는 유지.
2. **\`heroProof.outcome.worse\`가 입증한 상품 제거 반사실 비교** — \`상품이 없었으면 중상, 현재 퇴각\`은 동일한 기록 RNG 증거로만 확인한 비교이므로, 마치 실제로 중상이 먼저 일어났다가 치료된 듯 표현하면 거짓. 이때 첫 인쇄는 *비교한 미보급 결과의 흔적*이라는 표현을 구분하거나, 더 안전하게 최종 스탬프만 찍고 아래에 \`{상품} 덕분에 중상을 피했다\`를 붙인다.
3. **상품이 위험을 완화했으나 Outcome 차이는 UNPROVEN인 경우** — 중상/사망 스탬프를 지어내지 않는다. 기존 결과를 보이고 실제 대응·피로 완화만 사실대로 서술. \`combatHero\`만 있는 승리도 중상→성공처럼 만들지 않는다.

### 9-10-4. 판단 재미 — 가격과 재고의 기회비용을 선택 직전에 읽게 하기

**직접 수정안 3-A: SALE 가격 3버튼에 '현재 이익 vs 관계' 두 축.**
- 현행 Source `dist/ui/app.js::priceKeys`의 각 가격 키는 이미 `할인/정가/바가지·실제 가격·이익 G`를 보여 준다. 단골도 변화는 거래 후 `SALE §TRANSACTION RESULT`의 영수증 스텁과 NPC 기록에 남는다.

- 목표: 같은 물건을 할인/정가/바가지에 팔 때 금전과 관계의 차이를 **가격 누르기 전** 플레이어가 이해하는 것. 정확한 구매 확률, 미래 승리, 정답 SKU, 관계 투자 성공 보장은 제시하지 않는다.

**직접 수정안 3-B: 마지막 재고 × 남은 손님을 보이는 곳에서만 충돌시키기.**
- SALE에는 이미 각 `재고 N`과 손님 대기 수가 따로 있다. 현재 선택 상품이 **해당 SKU의 진짜 마지막 1개**이고, 아직 **뒤에 처리할 방문자 1명 이상**이 있을 때만, 선택 트레이/상품 메타의 기존 빈 공간에 `마지막 재고 1개 · 뒤에 손님 {N}명` 1줄을 추가하는 안.
- 마지막 재고 판단은 화면의 `groupStock` 합산 상품량과 실제 SALE 소비량을 동일 기준으로 사용하며, 똑같은 SKU가 여러 배치로 나뉘어도 `1개`를 거짓 표시하지 않는다. 남은 손님은 `queue.length - cursor - 1`; 구체적 미래 손님 정체/직업/목적지 미리 보기 금지(`SALE §QUEUE INFORMATION BOUNDARY`).

- 목표: 현재 손님 지원 vs 나중 손님 재고 보존이라는 자원 배분 딜레마를 자연스럽게 드러내는 것. 알고리즘/확률/판매 가능 여부/가격 공식 변경 없음.

**설계 실패 조건:** 희소 재고 문구가 눈에 띄어 플레이어가 습관적으로 판매를 회피하거나, 가격 키의 밀도가 높아져 핵심 효과가 안 읽힌다면 두 안을 별도로 철회할 수 있어야 한다. PRICE/마지막 재고는 독립 작은 패치. 채택 후 UI_UX §SALE / SALE §PRICE ROLE · §ITEM SELECTION / COPY_AUDIT / 판매 회귀, 화면 360·390·430 검증.

### 9-10-5. 30일 반복 피로 — 의미 있는 결정 유지, 무의미한 결과 반복만 단축

**직접 수정안 4-A: 두 번째 Run부터 사용 가능한 선택형 '주요 NIGHT 결과만 보기' (미승인).**

- 모든 NIGHT 결과가 단순하면, 결과 N건을 생략한 사실만 기존 rail에서 알리고 NIGHT→Closing이 **자동 결정 없이** 기존 `마감으로` 클릭으로 닫히도록 한다. Save/Resume, 중간 DAY 진입, 다회차 설정 지속, reduced-motion을 함께 확인.

### 9-10-6. 애착·실패·재플레이 — 기록을 한 번 더 찾게 하지 말고, 꼭 필요한 순간에 돌아오게 하기

**직접 수정안 5-A: 의미 있는 결과를 낸 손님의 다음 방문에서 1줄 회상.**

**직접 수정안 5-B: 실패 END 이유를 한 줄만 더 구체화.**
- 현행 `dist/ui/app.js::endHeadline / endBanner`는 사망 한도/운영비 부족이라는 종료 이유를 말하지만, END `이 점포의 기록`의 `돌아오지 못한 사람`은 숫자만 보여 준다. 이 원칙은 기존 User가 숫자 중심의 A안으로 승인한 사항이므로 **이 안은 변경 승인 필요**.
- 제안은 기록 블록을 새로 만들거나 손실을 소설처럼 설명하는 것이 아니다. `s.endReason` 바로 아래 **실제 상태로 확인한 최신 폐점 한 줄**을 선택적으로 배치:
  - 사망 한도: `DAY {N} · {마지막으로 떠난 실제 NPC 이름}가 돌아오지 못해 누적 {사망}/{허용}명`처럼 **기록된 마지막 사망자와 숫자만**. 한 밤에 여러 명이 죽었다면 '마지막으로 떠난 사람' 한 명만 밝히고 나머지는 기존 수첩에 남긴다. 새롭고 부정확한 원인 추정 금지.
  - 파산: `마감 골드 {금액}G · 운영비를 감당할 수 없었다`처럼 실제 종료 금액만. 내 돈이 왜 줄었는지 도출할 근거가 없으면 폐기·상품이 원인이라고 단정하지 않는다.
  - Final 패배: 이미 `sentOff()`가 출전 대원·마지막 상품을 보여 주므로 **추가 원인 줄 없음**. 결과표가 제공하지 않는 부족 능력치를 만들어 책임을 돌리지 않는다.
- END의 `이 점포의 기록`과 재플레이 넛지, 숙련/자본 정산 순서·개수는 유지. 별도 챌린지·추천상품·정답 진단·마스터리 포인트 없음.

**왜 재플레이에 필요한가:** 가장 강한 NPC와 실제 잃은 손님을 기억하는 게 다음 Run에 판매·보급을 다르게 선택할 구체적인 동기가 될 수 있다. 다만 Run마다 NPC는 새로 생성되므로 `다음 판에 그 이름의 손님을 다시 구하라` 식의 거짓 미션을 약속하지 않는다.

**채택 조건:** 첫 HERO급 회상 직후 재방문 시 NPC를 알아보는지, 실패 후 어떤 선택을 바꿀지 유저가 말하는지. 소규모 체감 개선이 없거나 반복 잡담만 늘면 폐기. 관련 owner NPC_TRAIT/SALE/UI_UX/COPY_AUDIT/NIGHT_CLOSING, QA의 증명·세이브·모바일·이벤트·END 기록 확인.
